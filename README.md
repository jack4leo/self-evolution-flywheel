# Self-Evolution Flywheel

This is a **reusable agent workflow skeleton** for any software repository. It extracts maintenance mechanisms rather than Magpie business rules: entry routing, project-facts documentation, evidence-based coding standards, community-contribution review, a subsystem map, and an error log and daily review continuously maintained by agents.

> The general guardrails in the template can be used directly; project-specific architecture, commands, risk boundaries, acceptance rules, and Lessons must be verified and generated by the agent in the target repository, not invented from the template or another project.

The Markdown documentation in this repository has been unified in **English**.

## Using It in a New Project

1. On GitHub, select **Use this template** to create a project copy, or clone this repository locally. The template copy includes documentation, prompts, review scripts, the Lesson-promotion gate, and Codex/Claude Code project-level startup hooks.
2. To install it in an existing project, run `./install.sh` from the target project's root. If the template is cloned separately, run `/path/to/self-evolution-flywheel/install.sh --target /path/to/your-project`. The installer adds missing files, including `scripts/` and `.github/workflows/lesson-promotion-gate.yml`, and preserves differing existing files. For an existing `AGENTS.md` managed-routing change or an additive Claude settings hook merge, it shows the exact proposed diff and asks `[y/N]` in an interactive terminal; only `y` or `Y` authorizes that change. Declining, EOF, or no interactive terminal preserves the original. Existing Codex settings still require a manual hook merge. Already-registered exact hooks are accepted, missing settings files are created, and skipping one provider does not block the other. Confirmed updates retain a recovery backup and fail closed if the snapshot or safe publication checks fail. See [`docs/installation.md`](docs/installation.md) for details.
3. In a Use-template copy, first run `./install.sh` once from the project root to create the dedicated `./.agent-maintenance/flywheel-install.sh` entry; verify that entry is the reviewed template installer, then explicitly run `./.agent-maintenance/flywheel-install.sh --bootstrap codex` or `./.agent-maintenance/flywheel-install.sh --bootstrap claude`. Running only `./install.sh` installs files and, when safe, hooks; a later startup hook only provides a reminder and does not begin filling documentation or preempt the user's task.
4. When bootstrap is explicitly requested, have the project agent fully execute [`prompts/bootstrap-project.md`](prompts/bootstrap-project.md). It checks the real source code, package manifests, CI, and existing documentation, then fills in `docs/project-profile.md`, the project-specific `docs/code-standards.md`, `docs/contributors.md`, and `docs/subsystems/`.
5. Have a maintainer verify the automatically collected facts, test commands, permission boundaries, and any product/security decisions requiring human judgment; unknown items must remain `UNKNOWN`, not guesses. On completion, the agent writes `.agent-maintenance/bootstrap-complete` with the reviewed HEAD SHA. Startup hooks stay quiet only while that marker is valid and the required project documents remain present.
6. Connect [`prompts/daily-review.md`](prompts/daily-review.md) to an agent/scheduler actually available to the project, and review commits each day since the last watermark. Each project chooses its own scheduler, model, credentials, and permissions; this template does not pretend that a directly runnable AI service exists.
7. Route each development task through `AGENTS.md`; maintain `LESSONS.md` during each review. By default, promote the same lesson to `docs/code-standards.md` as a stable rule only after it appears on **three different review dates**.

> Project-level hooks have code-execution permissions, and Codex/Claude Code may ask users to inspect and trust project settings; the installer does not bypass these confirmations. Before first enabling them, inspect `.agent-maintenance/session-start.sh` and the generated settings. Hooks validate the completion marker and required documents, then provide a reminder only; they do not start a model or write documentation on their own.

## File Map

- [`install.sh`](install.sh): Safely installs template files, merges startup hooks, and can explicitly start bootstrap once.
- [`docs/installation.md`](docs/installation.md): Installation scope, overwrite strategy, startup-trigger boundaries, and links to official tool documentation.
- [`AGENTS.md`](AGENTS.md): Short routing table; tells the agent what to read before work and what to do at completion.
- [`CLAUDE.md`](CLAUDE.md): Claude Code entry point; imports the shared routing table and Lessons without duplicating rules.
- [`LESSONS.md`](LESSONS.md): The target project's dynamic error log, maintained by the agent from real commits, rework, and verification evidence.
- [`docs/project-profile.md`](docs/project-profile.md): Project differences, verification commands, risk gates, autonomy boundaries, review archive location, and watermark.
- [`docs/code-standards.md`](docs/code-standards.md): Cross-project general baseline plus project-specific rules maintained by the agent from project evidence.
- [`docs/contributors.md`](docs/contributors.md): Security-screening framework for community PRs; project policies, lists, and decisions must not be invented by the agent.
- [`docs/subsystems/README.md`](docs/subsystems/README.md): Subsystem documentation index and maintenance protocol; specific pages are generated from the target project's source code.
- [`docs/maintenance-loop.md`](docs/maintenance-loop.md): The closed loop of initialization, daily development, PR review, daily review, and rule promotion.
- [`docs/automation/runner-contract.md`](docs/automation/runner-contract.md): Input/output and permission contract for connecting reviews to any scheduled agent.
- [`scripts/freeze-review-range.py`](scripts/freeze-review-range.py): Freezes a verified, read-only commit range and emits its canonical manifest and explicit path exclusions.
- [`scripts/write-frozen-review.py`](scripts/write-frozen-review.py): Writes archive and Lessons content for one frozen range; with paired promotion inputs, it also migrates promoted Lessons and writes stable rules to `docs/code-standards.md` before advancing the watermark as the final durable write.
- [`scripts/validate_lesson_promotions.py`](scripts/validate_lesson_promotions.py): Validates persisted Lesson IDs, evidence dates, citations, and promotion references.
- [`.github/workflows/lesson-promotion-gate.yml`](.github/workflows/lesson-promotion-gate.yml): Runs the persisted Lesson-promotion validator on pushes and pull requests; it does not run a retrospective.
- [`prompts/`](prompts/): Reusable task prompts for project initialization, development, PR review, and daily review.
- [`.github/PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md): Requires recording the goal, impact, verification results, and checks not run.

## Design Principles

1. **The entry point only routes.** Keep the root guidance short; put rules in the single authoritative document.
2. **Separate general rules from project facts.** Do not treat Magpie's technical details, specific test commands, or one project's product tradeoffs as general standards.
3. **Base documentation on source code, tests, and evidence.** Describe current behavior; mark proposals and unverified assumptions separately.
4. **Let errors become readable lessons before hard rules.** Lessons retain dates and evidence; promote project-agnostic rules into standards only after they reach the promotion threshold.
5. **People control direction and permissions.** An Agent may propose or maintain rules, but cannot treat unauthorized product decisions, security exceptions, contributor bans, or release permissions as its own decisions.
6. **Verify honestly.** State clearly which checks ran and which did not; select compilation, tests, and real integration verification according to the project's actual risk, and never claim work that was not done.

## The Template Is Not a Plug-and-Play Project Specification

Before a new project is initialized, `docs/project-profile.md` and the project-specific sections are blank placeholders. Run bootstrap first; do not treat placeholders as verified facts. This template repository is a public GitHub Template; the visibility and permissions of a template copy are determined by the repository owner at creation time, so do not assume it is private by default.
